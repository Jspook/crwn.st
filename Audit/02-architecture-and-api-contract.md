# crwn.st — Phase 0 architecture proposal / API contract (policy approved)

> **Phase Status:** ผู้ใช้อนุมัติแนวทางและ policy หลัง Phase 0; implementation และ migration ยังต้องผ่าน safety gate ของแต่ละคำสั่ง โดยเฉพาะห้ามเขียน shared DB · อ้างอิง [[2026-10-14 Pending Order Reentry Plan]] และ [[01-preflight-and-safety-report]]

## Confirmed boundary

- Canonical physical room = `resolveRoom(input).roomNumber` (`'1'`…`'10'`), QR barcode เป็น external alias. `FITTING_ROOM.FTR_Number` เก็บเลขห้อง; API URL/`roomId` ยอมรับ alias ที่ resolver รู้จักเท่านั้น. `GET /api/fitting-orders?roomId=<barcode>` ต้องเทียบเลขห้องจริง. Customer ต้องเป็นเจ้าของ active session; staff ต้อง role ถูกต้อง.
- Session ID ตอนนี้เกิดใน memory (`ses_...`) ขณะที่ MySQL ไม่มี session columns; release/TTL ไม่เปลี่ยนแถว. Live metadata: 6 rows (2 pending ตาม predicate เดิม), ไม่มี barcode-shaped room rows, ไม่มี session/cancel columns. ไม่ทราบว่าแถวใดอยู่ใน active session.

## Proposal for review (contract decisions, not implementation)

1. **Durable authority:** เพิ่ม additive `FITTING_ROOM_SESSION` registry keyed by session ID, unique active session per room ด้วย DB-enforced invariant ที่ออกแบบให้ MySQL version ใช้ได้; room number, customer ID, started/lastSeen/ended/expiry, terminal reason. `FITTING_ROOM.FTR_SessionID NULL` (FK/typing verify against live MySQL constraints), `FTR_CancelledAt NULL` + room/session/status-oriented index. ห้าม mutate legacy rows อัตโนมัติ. เสนอ DB เป็น source of truth สำหรับ active session; memory cache/lock เป็น optimization เท่านั้น. ต้อง inventory DB version, concurrency/uniqueness และ rollout compatibility ก่อน DDL.
2. **Enter/resume:** Customer acquire room; session เดิมของเจ้าของที่ยัง active ให้ resume ID เดิม, คนอื่น 409; expired/stale ให้ปิด session เดิมใน DB ก่อนให้ session ใหม่; restart โหลด/reconcile durable registry หรือ expire อย่าง explicit, ห้ามสร้าง S2 แล้วถือ S1 active พร้อมกัน. `routes/views.js:90-115` ที่ auto-acquire ต้องเข้าร่วม contract เดียวกับ POST enter.
3. **POST /api/fitting-orders:** require customer + active session of canonical room, bind new order to that session in DB. Create/release/staff PATCH serialize per room at DB authority (transaction/row lock หรือ equivalent) ไม่พึ่ง mutex process เดียว; revalidate after awaited variant lookup, before INSERT. หาก session ปิด → 409/403 โดยไม่สร้าง orphan. พิจารณา request-id/idempotency key สำหรับ retried POST หลัง response หาย.
4. **GET /api/fitting-orders:** customer query ต้องจำกัด active session, owner และ canonical room; staff feed return only rows whose `FTR_SessionID` equals active session of that room and not cancelled; legacy NULL ไม่เข้าปัจจุบัน. `myOnly`, `limit` ยังตาม contract เดิมสำหรับรายการที่อนุญาต. 200 `[]` หมายถึงตรวจสำเร็จและไม่มีรายการ ไม่ใช้เมื่อ DB/network/session lookup error (5xx/4xx).
5. **PATCH /api/fitting-orders/:id:** staff-only. Verify row session = active registry session under lock, cancelled NULL, ownership, allowed state transition. Conditional UPDATE รวม session/status/ownership predicate + ตรวจ `changes` แล้วคืน 409/404 เมื่อ stale; ห้าม complete หรือ reset pending ของ S1 ผ่าน retained card ใน S2. **Approved transition (ผู้ใช้ยืนยัน 2026-10-15):** pending→preparing (claim), preparing→complete (assignee), complete→complete idempotent เท่านั้น; ปฏิเสธ rollback ไป pending และ pending→complete โดยตรง. Existing `routes/api.js` ยังยอม reset pending/complete ตรง ๆ — ต้องแก้พร้อม regression tests; policy approved ไม่ใช่หลักฐาน implementation verified.
6. **Release:** warning query ต้องเกิดก่อน cleanup. Customer ส่ง sessionId ที่ตรงกับ active registry; staff force-release เลือก session active ใต้ lock. ภายใน transaction ปิด session S1 + cancel เฉพาะ `EMP_ID IS NULL AND FTR_FinishTime IS NULL AND FTR_CancelledAt IS NULL` ของ S1; commit สำเร็จแล้วจึง clear memory cache; retry same session returns defined idempotent success only if already ended (ไม่แตะ S2). DB error → rollback, return failure, occupancy ไม่ถูกปล่อยใน app; หาก crash ระหว่าง commit/clear ให้ reload/reconcile จาก DB ก่อนรับ create/enter. ไม่มี 200 แบบสำเร็จครึ่งทาง.
7. **TTL/restart:** expiry transition เดียวกับ release จาก durable registry, cancellation pending เฉพาะ session นั้น. ห้ามอ้างว่า TTL in-memory ลบ DB rows; reconcile job ต้องมี locking/idempotency และ instrumentation; S1 ที่หมดอายุ/ปิดแล้วมองไม่เห็นหรือ PATCH ไม่ได้ทันทีแม้ cleanup ล่าช้า. ถ้าไม่ต้องการ durable registry ต้องเสนอ alternative พร้อม proof ของ atomicity/restart และข้อจำกัด single-node ก่อนอนุมัติ.
8. **Customer UI:** query GET ของ active session เมื่อกดออก; pending/preparing → render warning ก่อน release, complete-only → completed modal, 200 `[]` → no-orders confirm. HTTP/network/parse error หรือ session invalid → แจ้งตรวจสอบไม่ได้ ห้าม release ผ่าน no-orders path. Cancel exit ไม่ส่ง release; confirm exit ย้ายหน้า/clear local state หลัง release success เท่านั้น. รองรับ response error ที่ status/code สอดคล้อง.
9. **Legacy:** newly nullable session column leaves existing 6 rows with NULL; keep queryable only via explicit historical/admin path if authorized, not current staff/customer feed or PATCH. ไม่ backfill จาก room/time/customer โดยเดา; pending legacy 2 rows ต้องมี business disposition แยก, preserving IDs/audit.

## Alternatives / user policy decisions required

| Decision | Recommended default | Other option / cost |
| --- | --- | --- |
| พนักงานรับงานแล้ว (`preparing`) แต่ลูกค้าออก | ไม่ auto-cancel; เก็บเป็นประวัติ ไม่ขึ้น Kanban session ใหม่; แจ้ง/จัดการงานค้างผ่าน staff workflow แยก | Auto-cancel ต้องกำหนด notification/stock/ack policy และอาจทำงานที่พนักงานกำลังทำสูญความหมาย |
| Legacy rows `FTR_SessionID NULL` (live 6, pending 2) | ไม่แสดง/รับใน active feed, ไม่เปลี่ยนข้อมูล; ส่งให้ตรวจ manual disposition | Backfill อัตโนมัติเสี่ยงโยนงานเก่าให้คนในห้องใหม่ |
| Older client release ไม่มี `sessionId` (`test/room-exit.test.js:166-177`) | Require explicit sessionId for customer; older clients 400/409 + refresh UX; staff force-release แยก | Compatibility owner-only resolve current session server-side (ไม่รับ session stale อย่างเงียบ ๆ) ต้องออกแบบ/review และมี security tests |
| Lifecycle authority | DB session registry เพื่อให้ release/create/expiry ใช้ transaction/locking และ restart-safe | Memory-only + order tagging กัน reentry ได้บางส่วน แต่ pending cancellation แบบ guaranteed/atomic ข้าม crash ยืนยันไม่ได้ |
| `complete` / status reset | **อนุมัติ:** complete immutable; no rollback to pending; ห้าม pending→complete โดยตรง | Staff UI ปัจจุบันมีปุ่ม pending→preparing→complete; ยังต้องตรวจ caller อื่นก่อน rollout |
| Tests with writes | mock suite ก่อน; isolated DB ใหม่ที่ไม่มีข้อมูลผู้ใช้เมื่อได้รับ approval | `npm run test:integration` ปัจจุบันเขียน shared DB ได้และ guard DB-name ผิด ห้ามรัน |

- **A01 + B02 RED:** tests บน mock (tracked `test/` recommended; ห้ามเขียนทับ ignored `tests/` โดยไม่ inspect); สร้าง behavior cases แยกและ flow ร่วม. ต้องเห็น intentional RED ก่อน production edit.
- **B03/B04/B05 Backend (one owner / isolated worktree):** `routes/api.js`, `routes/views.js`, `utils/roomOccupancy.js`, `database/db.js`, new additive migration, `database/schema.sql`, backend tests. เสนอ migration & legacy impact ให้ Lead review ก่อนแตะ schema. Integration merge หลัง contract freeze.
- **A02/A03 Customer UI (other worktree or sequential):** `views/customer/fitting-room.ejs` และ client tests; อย่าแก้ `routes/api.js` ซ้ำกับ Backend. A02 normalization ฝั่ง server อยู่กับ Backend; UI agent consume approved contract.
- **A04/B06:** independent diff review, GREEN mock tests, isolated integration/UI เฉพาะหลัง scope/test DB approval; no live write/migration/deploy. `git diff --check`, recheck ignored test/report persistence.
