## Shared invariant: room identity and occupancy (BUG-007 → 006 → 001)

**Evidence:** `routes/api.js:317-340,455-554`, `routes/views.js:88-116`, `public/js/app.js:196-260`, `schema.sql:102-127`.

1. **Identity decision (BUG-007):** approve authoritative QR string ↔ logical room registry for four physical rooms, using actual QR payload inventory, not guessed IDs. Current four hard-coded identifiers map to 1–4 already, but code copies mapping and stores external ID in `FTR_Number`. Recommended low-risk first stage: one shared server resolver (`routes/api.js` and `routes/views.js` consume same module; frontend asks server), accept only exact approved raw QR strings plus deliberate legacy logical aliases, return canonical `{qrId,roomId,roomDisplay}` and explicit invalid-room 4xx. Keep IDs as strings (leading zeros); do **not** strip arbitrary non-digits or default to room 1 (`app.js:196-207`). Do not assume `53636636373363` is room 1. Alternative: DB `ROOM` registry with unique `qr_id` and unique logical number for admin editability/multi-instance deployments; extra migration/complexity but enforceable constraints. Decide after physical inventory. Legacy unknown `FTR_Number` needs read-only count/backfill mapping proposal before write; allow staged read compatibility, then canonical writes, only then optional migration. Rollback: restore previous resolver and read compatibility; snapshot/backup before any approved data rewrite. Reject duplicate QR or logical room mappings at startup/deployment, unknown QR 400/404. Security note: a publicly readable QR string alone is not proof of physical presence; access policy needs product decision.
2. **State decision (BUG-006):** durable occupancy belongs in DB (single source across workers/restarts), request/delivery rows remain history; localStorage only a UI hint. `occ_` is an occupancy row prefix (`api.js:512-519`), not an unexpected column. Recommended incremental path: keep current table for compatibility initially but perform enter/resume/release in `withTransaction` (`database/db.js:48-79`), lock a stable per-room registry row (`SELECT ... FOR UPDATE`) or use a separate `ROOM_OCCUPANCY` table with `room_id` UNIQUE/PK and one active owner/session, rather than trying to lock missing rows in `FITTING_ROOM`. Explicit active-session ownership and atomic transition; same owner enter resumes same session (not release/recreate), different owner gets 409. Release targets that session/owner and only pending/preparing requests; completed history retention policy must be explicit. Staff force-release must be audited and confirm current session. Return success only after commit; handle zero affected rows/idempotent retry explicitly. Use UUID request IDs or DB-generated collision-safe IDs rather than `Date.now()` (`api.js:512,609`). Store created/last-seen/expires fields only if lease policy approved. If no lease allowed, operator-mediated recovery must still be defined; never automatically free an actively used room solely on browser Back/refresh.
   - Alternative A: leave sentinel in `FITTING_ROOM`, add conditional unique active marker / transactional row lock. Smaller schema, but MySQL nullable/partial-unique semantics and mixed row roles complicate correctness; prove race safety before choosing. Alternative B (preferred if concurrency/repair is critical): separate `ROOM` registry + occupancy/session table, FK to request rows; more migration and rollback work, clearer invariants. **Do not delete `occ_` blindly**; inventory historical rows, create compatibility reads, migrate only after backup/dry run/approval, record counts/checksums, switch writes, verify, retire old rows only in later approved release. Rollback app feature flag/read-path; migration rollback must preserve new events, not just DROP tables.
   - DB outage: `GET /api/fitting-rooms` currently converts query failure into empty occupancy (`api.js:457-461`); fail closed (503) rather than advertise free. Response should carry `canResume` for authenticated owner without exposing owner identity to others. Server restart must recover from persisted state. Lease expiry, heartbeat cadence, grace period and staff reconciliation are product decisions.
3. **Navigation decision (BUG-001):** distinguish intentional Exit from Back/Refresh/brand-link. Never release on `beforeunload` alone (unreliable and could release on refresh). On dashboard, expose owned active room as **Resume**; render fitting page via server-authoritative session (`views.js:111-116`) and do not start another session. On explicit Exit, await `release`, check `res.ok`/JSON success, navigate only after commit; failure displays retry/recovery. On room enter, stop on failed HTTP response rather than navigate (`app.js:255-260`). Browser Back simply changes page, ownership persists until explicit Exit, approved expiry, or audited staff recovery. Test Back/Forward/BFCache, Refresh, two tabs, direct URL and network failures. Alternative history interception may improve UX but cannot substitute durable resume/lease; no need for broad router refactor. Rollback UI change independently while retaining compatible server contract.

**Dependencies/risk:** room identity must be canonical before new occupancy constraints. Live schema and current rows may contain unknown IDs; inventory before migration. Multi-process race and cross-session release are high-risk, require isolated MySQL tests and staged rollout. Source touchpoints: `routes/api.js` room + order paths; `routes/views.js`; `public/js/app.js`; `views/customer/{dashboard,fitting-room}.ejs`; `views/staff/fitting.ejs`; `database/schema.sql`, migrations **only if approved**; new shared module name TBD, do not pre-create it.

## BUG-004 — variant selection/employee mismatch

**Evidence:** two real p1 pairs `database/seed.js:607-623`; independent controls + fallback `public/js/app.js:375-451`; POST DB join `routes/api.js:583-631`; staff joins SKU `:351-372`. **Confirmed code defect.** Recommended: model selectable options as actual `ITEM_VARIANT` rows with stock > 0, not Cartesian product. Choose size then filter available colors (or present SKU-backed variant choices); if exact pair absent, disable submit with explicit error; never silently substitute size-only/color-only/first SKU or synthesize SKU (`app.js:446-451`; `fitting-room.ejs:241-260`). API receives SKU as canonical and, if size/color included, verifies exact equality with DB variant (or drops redundant fields from request contract and always returns DB values). Ensure product/variant ownership and stock validated server-side. Use server-returned SKU/size/color for customer toast/record, not original invalid UI pair (`app.js:483-495`). Duplicate request behavior: define idempotency key/session+SKU policy; choose unique client request key if retry must not create duplicate order; test concurrently. Alternative client-only filtering is cheaper but forged/stale payload can still mislead; client+server invariant is recommended. No schema change required for pair validation; dedupe key may need approved unique column/index. Rollback both client and server behind compatible response shape; no mass SKU data changes. Tests R04 in [[05-regression-test-plan]].

## BUG-002 — cart image identity

**Evidence:** `utils/productImages.js:6-25`; `routes/api.js:216-241,248-285`; `public/js/cart.js:54-73,97-125,212-219`. **Confirmed category-image mismatch after server rehydrate**, variant-photo requirement **unverified**. Recommended minimum: include `ITM_ID`, `ITM_Tag` and resolved image in authoritative GET cart join, using *same* resolver as product API; group by SKU; browser uses server image, never derives product from barcode or assumes `top-*`. Existing localStorage records should be reconciled by SKU from server; if server unavailable, mark image as provisional, do not claim authoritative. Validate all SKU/quantities before replacing cart and wrap delete+insert in transaction; check HTTP status and revert/refetch on failure. Alternative storing image URL per cart row duplicates derived data and becomes stale; avoid unless real color-specific media catalog exists. If color-accurate photos are a requirement, obtain asset-to-variant mapping spec and plan separate `ITEM_VARIANT` image relation/migration (approval) rather than fake color-specific imagery. Rollback response additive fields and UI fallback separately; protect existing cart data with transaction. Tests R02; small code task except persistence safety.

Then audit live rows via read-only query in [[02-bug-investigation]], compare seed. If approved, modify only identified seed records and apply narrowly scoped, reviewed SQL to confirmed live IDs/values in a DB transaction (backup/preview affected-row count; assert expected count; rollback on mismatch). Do not rerun `database/seed.js`—it TRUNCATEs product/orders/fitting/cart tables (`:49-57`). Alternative add UI `ITM_Tag!='skirt'` exclusion for Male is a masking rule that silently hides legitimate unisex items; not recommended. No schema change needed unless product requirements call for multi-audience categories; then design separate normalized taxonomy as a separately approved project. Rollback: restore before-values only for reviewed IDs, never indiscriminately reseed. Tests R03.

## BUG-005 — completion timestamp contract

**Evidence:** DDL `FTR_FinishTime` (`database/schema.sql:108-113`), PATCH `NOW()` (`routes/api.js:681-700`), GET omits it (`:351-359`), card uses `createdAt` (`views/staff/fitting.ejs:150-151`). **Confirmed display/API omission, NOT confirmed DB missing.** Recommended first validate live schema and an isolated completed row. Add `finishedAt` to GET from `FTR_FinishTime`; complete card uses it (with explicit missing-data state, never current time fallback). Sort complete by finish time if label means recently delivered (`api.js:413-443`; `staff/fitting.ejs:121-129`). Enforce state transitions atomically: pending→preparing by staff; preparing→complete set finish time once with conditional UPDATE and affected-row check; reject/define repeat complete and reverse transitions; do not overwrite finish time silently. On DB error return failure, never success before persisted write. Alternative just add SELECT/display is smallest but leaves repeat-update/audit defect; phase changes with tests, no new column expected if live schema matches. Confirm timezone storage/serialization policy (MySQL DATETIME + mysql2/browser). Historic null timestamps require evidence-backed handling; do not fabricate dates. Rollback additive GET field/UI, restore previous transition endpoint only with careful client compatibility. Tests R05.
