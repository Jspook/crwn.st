## BUG-001 — Browser Back leaves room occupied

- **Repro proposed, not executed:** customer scans known room → `/enter` succeeds → browser Back to dashboard (not UI Exit) → open room modal → same room marked occupied; try direct URL `/customer/fitting-room?roomId=<known>` and refresh separately.
- **Evidence:** Browser navigation is `window.location.href` (`public/js/app.js:255-260`); explicit Exit alone calls `/release` (`views/customer/fitting-room.ejs:270-308,406-421`); browser Back/brand link has no release handler (`views/partials/navbar.ejs:6-27`); occupancy remains from `occ_` insert (`routes/api.js:512-521`) and `GET /fitting-rooms` checks present rows (`:457-479`); `selectRoom` blocks **any** occupied room before trying same-owner enter (`app.js:240-250`), while server `/enter` allows same owner but starts a NEW session (`api.js:503-519`). Direct fitting view checks active owner and room (`routes/views.js:111-116`).
- **Root cause:** navigation does not mean intentional exit; dashboard lacks resume-for-owner path. Session persists while preflight treats own active room as another's. **Confirmed (code)**; user report of inability to return via UI consistent; direct URL may work and must be tested. Separate failure: enter/release fetch results ignored (`app.js:256`; `fitting-room.ejs:302-308`), so failure can redirect without a valid state.
- **Severity:** High; room availability + customer lockout. **Impact:** blocks UI re-entry, accumulates stale room occupation. **Difficulty:** Medium; coupled to BUG-006/007. **Unknown:** actual browser BFCache/history, DB state, network status, session expiry policy. **Next tests:** browser Back/Forward/Refresh, intentional Exit, same-owner resume, other-owner conflict, release failure, server restart, stale lease.

## BUG-002 — Wrong cart image

- **Repro proposed:** add `skirt` or `outerwear` SKU to cart, note original image, reload/login so server cart replaces local cart, compare. Select two colors of same product and compare with expected real media specification (if any).
- **Trace:** product lookup adds mock image from `getProductMockImage(tag,id)` (`routes/api.js:176-188`; `utils/productImages.js:6-25`) → `Cart.addItem` persists image locally (`public/js/cart.js:97-125`) → POST `/api/cart` persists *SKU only* (`routes/api.js:248-285`, schema `PAY_CART_ITEM`) → GET joins SKU→variant→item but does not return `ITM_ID`,`ITM_Tag` or image (`api.js:216-241`) → `Cart.init` derives productId via `sku.split('-')[0]` (numeric EAN SKU stays numeric), then assigns **top** mock image (`cart.js:54-73`) → drawer renders `item.image` (`cart.js:212-219`). This deterministically loses original category picture after a successful reload. POST errors are swallowed/optimistically shown (`cart.js:81-125`); API deletes old rows before validation (`api.js:261-288`), an adjacent data-loss defect.
- **Root cause:** server/cart contract loses stable product image identity; fallback assumes top and guesses product ID from SKU. **Confirmed (code)** for category mismatch; variant-color fidelity is **Unverified** because schema and mock assets have no color-specific image mapping. **Severity:** Medium; misleading catalog/customer experience. **Difficulty:** Low–Medium; image data contract + cart sync. **Unknown:** live SKU/media data, target photo policy. **Tests:** initial add vs reload for skirt/top/bottom, two products, colors, API failure rollback, old localStorage entries.

## BUG-003 — Skirt in Male

- **Repro proposed:** load `?category=male` product API, find skirt tags; compare `ITEM` on authorized read-only connection. Do not run seed.
- **Evidence:** seed has *five* `ITM_Tag='skirt'` with `ITM_Category='male'`: `p52` (`database/seed.js:470-476`), `p54` (`:486-492`), `p56` (`:502-508`), `p58` (`:518-524`), `p60` (`:534-540`). Script counts 67 seed items, 10 skirts, 5 male skirts. `database/seed.js:600-604` writes both fields; `routes/api.js:29-33` filters exact `ITM_Category`; fitting UI filters same field (`views/customer/fitting-room.ejs:53-59,73-80`). No evidence of logic mixing tag/category for this symptom. `p4` mentions skirts in its **description** but is a T-shirt: not an affected skirt product (`seed.js:86-92`).
- **Root cause:** source seed classification mismatch *if* intended business policy is that those skirt SKUs belong exclusively to Female. **Likely** until merchandising policy and live DB verified; do not infer gender designation from clothing type alone. **Severity:** Medium. **Difficulty:** Low after policy sign-off; data migration approval required. **Unknown:** current `ITEM` rows, alternative unisex policy, additional live affected IDs. **Safe read-only SQL:** `SELECT ITM_ID, ITM_Name, ITM_Category, ITM_Tag FROM ITEM WHERE ITM_Tag='skirt' ORDER BY ITM_ID;` **Tests:** classification fixture/seed assertion and API filter for approved audience rules.

## BUG-004 — Requested size/color differs from staff SKU

- **Repro proposed:** with seed-like p1 variants XL/Black and S/Navy, choose XL + Navy in request modal, submit, compare success toast/customer tried item vs staff card.
- **Trace/evidence:** p1 pairs exist as separate SKUs (`database/seed.js:607-623`); modal independently renders unique sizes/colors (`public/js/app.js:375-398`) so permits nonexistent cross-product. `submitItemRequest` on no exact match falls back to size-only, color-only or first variant but sends originally selected size/color with fallback SKU (`app.js:440-470`); optimistic local item/toast retain requested pair (`:483-495`). Backend validates that SKU exists/in stock but ignores requested size/color when storing (`routes/api.js:559-614`); staff GET joins saved SKU to `ITEM_VARIANT` (`:351-372`), EJS displays DB size/color (`views/staff/fitting.ejs:183-190`). Response POST may return DB pair (`api.js:616-642`), creating contradictory client message.
- **Root cause:** UI generates invalid combinations then silently substitutes a different SKU; absence of invariant check against optional size/color at API boundary. **Confirmed (code)**, runtime manifestation pending. **Severity:** High; wrong garment delivered. **Difficulty:** Medium; BUG-006 session prerequisite. **Unknown:** actual variant stock and duplicate submissions under concurrency. **Tests:** exact valid pair, invalid XL/Navy rejected without write, out-of-stock, no variant, double click/idempotency, staff/customer same SKU/pair.

## BUG-005 — Missing delivery completion time

- **Repro proposed:** create order in isolated DB, change pending→preparing→complete, SELECT persisted `FTR_FinishTime`, GET order and read complete card time; repeat complete to test immutability.
- **Evidence:** DDL **has** `FTR_FinishTime DATETIME` (`database/schema.sql:102-113`); PATCH complete sets `FTR_FinishTime=NOW()` before HTTP response (`routes/api.js:681-700`). GET only selects `FTR_OrderTime as createdAt` (`:351-359`); card shows `createdAt` for every status (`views/staff/fitting.ejs:150-151,174-180`). Complete list sorted by *order* time (`api.js:413-443`; `staff/fitting.ejs:121-129`). PATCH permits any named status, repeat complete overwrites finish time, complete→preparing leaves finish time unchanged and status still complete (`api.js:656-700`).
- **Root cause:** **Confirmed (code)** for *missing displayed/API completion time* and mutable/incoherent transitions. Claim that DB *never records it* is **Unverified / contradicted by normal code path**; requires live schema/data verification. **Severity:** Medium–High for audit trail. **Difficulty:** Medium; contract + state transition. **Unknown:** live schema, failed writes, timezone conventions, historical completed rows. **Safe SQL:** `SELECT COUNT(*) AS completed, SUM(FTR_FinishTime IS NULL) AS missing_finish FROM FITTING_ROOM WHERE ITV_SKUID IS NOT NULL AND EMP_ID IS NOT NULL;` (does not distinguish pending vs preparing; use only as exploratory aggregate). **Tests:** persistence readback, GET finishedAt, UI time, repeat complete, rejected invalid transitions, DB failure no successful response.

## BUG-006 — `occ_` and fitting-room state

- **Repro proposed:** enter known room once/twice and inspect *isolated* DB rows/status; race two distinct customers; restart server; intentional exit; cleanup/TTL. No production mutation.
- **Evidence:** `FTR_OrderID` PK is shared by request rows and NULL-SKU occupancy sentinel (`schema.sql:102-117`; `routes/api.js:512-519`). `occ_` is row **prefix**, not column. Enter writes `FTR_SessionID`, `CUS_ID`, presence; new same-owner enter marks *unfinished* rows released (`api.js:498-519`). Release marks unfinished rows released but clears presence on **all rows in room**, not session-scoped (`:528-549`); completed rows may remain `FTR_ReleasedAt IS NULL` and appear in staff GET (`:377-381`). No unique active-room constraint or TTL in DDL (`schema.sql:102-127`); occupancy is `SELECT DISTINCT` and failed query is treated as available (`api.js:455-479`). Both enter and release perform nontransactional multi-step writes. `FTR_OrderID` uses millisecond `Date.now()` for occ and fitting requests (`api.js:512,609`), collision possible.
- **Root cause:** **Confirmed (code)** state model mixes occupancy and delivery orders and permits inconsistent transitions; concurrent double-booking/stale locks are **Likely** until stressed in isolated DB. **Severity:** Critical/High (availability & concurrency); **difficulty:** High. **Unknown:** live actual columns, indexes, occupancy rows, contention, server restart outcome, expiry/retention policy. **Data placement:** retain durable occupancy/ownership in DB for multi-process exclusivity and restart recovery; move only presentation/ephemeral UI state to browser/app memory. Avoid blind deletion of `occ_` records. **Safe SQL:** `SHOW CREATE TABLE FITTING_ROOM;` plus `SELECT LEFT(FTR_OrderID,4) AS prefix,FTR_Number,COUNT(*) AS n,SUM(FTR_CustomerPresent=1 AND FTR_ReleasedAt IS NULL) AS active FROM FITTING_ROOM GROUP BY prefix,FTR_Number;` redact identifiers/customer IDs in shared output. **Tests:** atomic enter race, owner resume, release scoped to session, stale lease, partial write rollback, completed order history.

## BUG-007 — QR identifier incorrectly used as room number

- **Repro proposed:** scan actual QR for each physical room; compare raw text, stored `FTR_Number`, roomDisplay in customer/staff, and unknown/leading-zero QR behavior; test user-provided example `53636636373363` **only as literal string**, never numeric normalization.
- **Evidence:** four hard-coded external identifiers map to display 1–4 (`routes/api.js:317-340`, `routes/views.js:88-109`, `views/customer/fitting-room.ejs:1-12`); `FTR_Number` stores normalized *external* ID on enter/order (`api.js:492,516-519,569-614`). Unknown ID is passed through and displayed by regex fallback (`api.js:329-340`); QR parser strips non-digits and silently defaults to `'1'` for malformed input (`public/js/app.js:196-207`). Client can proceed with unknown ID if absent from room list (`app.js:240-260`), backend does not allowlist (`api.js:489-519`). Thus mapping **partially exists**, but not as single canonical registry; unknown IDs can become raw room identifiers. The example `53636636373363` is not among four known IDs in checked source; do not assert its meaning without actual QR spec/registry.
- **Root cause:** **Confirmed (code)** missing rejection/canonical mapping for unknown QR + duplicated mapping; specific reported row/example **Unverified** without live DB/physical QR. **Severity:** High (misrouting/room collision); **difficulty:** Medium–High depending migration. **Unknown:** actual QR payloads, historic `FTR_Number` values, mapping ownership, whether leading zeros meaningful. **Tests:** all four IDs, full URL vs raw input per approved spec, unknown, malformed, leading-zero string, duplicate mapping, legacy records, staff display and API guard.

## Cross-bug conclusions

- BUG-001/006/007 share room identity + session/occupancy lifecycle. Stabilize canonical QR→room resolution and atomic durable occupancy before optimizing UI navigation.
- BUG-004/002 share SKU as authoritative identity; invalid pair substitution and missing image data are separate causes. BUG-003 is seed classification/policy, not variant mapping.
- BUG-005 is delivery event semantics; do not conflate with `FTR_ReleasedAt` (room/session release).
- Browser/log evidence still missing; live DB + HTTP contracts are now verified ([[08-live-db-verification]]), but do not call production **user-visible** root causes confirmed until T00-level browser and concurrency tests run.
